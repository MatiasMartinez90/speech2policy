└─ FLUJO DE AUTENTICACIÓN:
   1. Usuario se registra/login en Cognito
   2. Cognito retorna JWT token con claims
   3. Frontend envía token en header: Authorization: Bearer {token}
   4. API Gateway valida token contra Cognito
   5. Si válido, agrega claims a requestContext de Lambda
   6. Lambda extrae user_id del JWT: email = claims['email']
   7. Lambda usa user_id para acceder a DynamoDB

NO HAY TRIGGER DE LAMBDA PARA SINCRONIZAR CON POSTGRESQL
- Razón: No se usa PostgreSQL, se usa DynamoDB
- Los datos se guardan directamente en DynamoDB en el primer acceso

FLUJO DE DATOS - EJEMPLO: USUARIO RESPONDE PREGUNTA
================================================================================

1. Usuario autenticado hace pregunta sobre un curso
   └─ Request: POST /api/tutor/ask
      Headers: Authorization: Bearer {jwt_token}
      Body: {
        "course_id": "image-gen-bedrock",
        "section_id": 2,
        "question": "¿Cómo configuro el bucket S3?"
      }

2. API Gateway valida JWT
   └─ Valida token contra Cognito User Pool
   └─ Si válido, agrega claims a requestContext

3. Invoca tutor-handler Lambda
   └─ Extrae user_id: "maria@example.com"
   └─ Verifica rate limits en UserUsage table
   └─ Obtiene contexto de curso en CourseCatalog table

4. Envía pregunta a Claude (Bedrock)
   └─ System prompt: personalidad del tutor + contexto del curso
   └─ User prompt: pregunta del usuario
   └─ Temperature: 0.7, max_tokens: 2000

5. Claude responde
   └─ Response: "Para configurar S3 debes crear un bucket..."

6. Guarda sesión en TutorSessions
   └─ PK: SESSION#maria@example.com#s123
   └─ SK: TIMESTAMP#2025-11-06T14:30:00Z
   └─ Items: question, response, tokens_used, latency_ms

7. Actualiza UserProgress (si es validación de checkpoint)
   └─ PK: USER#maria@example.com
   └─ SK: COURSE#image-gen-bedrock
   └─ Incrementa contadores y scores

8. Retorna respuesta al frontend
   └─ Response: {
        "answer": "Para configurar S3 debes...",
        "tokens_used": 142,
        "stop_reason": "end_turn"
      }

COMPARACIÓN: DYNAMODB vs POSTGRESQL
================================================================================

DYNAMODB (ELEGIDO):
✅ Escalable automáticamente
✅ On-demand pricing (sin costo mínimo)
✅ Serverless (no hay servidores que gestionar)
✅ Latencia: millisegundos
✅ Point-in-time recovery
✅ TTL para limpieza automática
✅ AWS-managed encryption
├─ Queries limitadas (sin SQL completo)
├─ Joins no soportados (se resuelve con diseño)
└─ Schema semi-flexible (evolution friendly)

POSTGRESQL (DESCARTADO):
❌ Requiere RDS instance (costo fijo 24/7)
❌ Gestión de backups más complicada
❌ Escalabilidad manual
❌ Requiere AWS Lambda trigger (complejidad)
✅ SQL completo
✅ Joins nativos
✅ Relaciones complejas
✅ ACID garantizado

CONCLUSIÓN: Para este caso de uso (progreso de usuarios + catálogo), 
DynamoDB es mejor opción. Es más barato, más fácil, y más escalable.
